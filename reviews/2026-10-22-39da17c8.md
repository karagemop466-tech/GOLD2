## Findings for integration

### R39-01 — Medium — category subpages are absent

**Observed:** navigation contains one flat `rings.html` research page; diamond type is only a column. There are no category subpages.

**Requirement:** the user requested subpages organized by category.

**Requested disposition:** add category indexes/pages during integration, or explicitly keep this as an open requirement gap on Flagged for Review. Do not describe the current two-row page as a complete categorized catalog.

### R39-02 — Medium — checklist silently narrows “ring weight”

**Observed:** `scripts/build.py` generates the checklist weight rule as “grams of gold alloy excluding stones and other components.” The user's checklist asks for the **ring's weight in grams**. The catalog column likewise says “Metal weight (g).”

**Risk:** metal-only weight is useful for a contained-gold calculation, but replacing gross ring weight changes the requested field and could cause a listing's total ring weight to be discarded rather than recorded with an appropriate label.

**Requested disposition:** retain `ring_weight_grams` exactly as requested, with variant/size context; add a separate `gold_alloy_weight_grams` only when officially provided. Never derive one from the other. For nominal contained-gold calculations, clearly identify which verified weight basis is used and avoid counting stones/non-gold components.

### R39-03 — Medium — calculator cannot currently produce a user-facing calculation

**Observed:** the only UI control selects one of two products; both have null weight and null gold-price inputs. There are no labeled fields for a user to supply a verified weight and separately sourced price. The JavaScript arithmetic function is unit-tested, but every current UI path returns blank.

**Risk:** the requested calculator exists mathematically but is not usable for any actual calculation.

**Requested disposition:** add clearly labeled user-input controls (without treating user input as an official product observation), unit selection, formula, source/date fields for any metal quote, and invalid/missing-input tests. Keep all catalog-derived values blank until evidence exists. Cite [NIST's conversion](https://www.nist.gov/document/precious-metals-conversion-information-march2015pdf) if converting a troy-ounce quote to grams; never use NIST's illustrative prices as current quotes.

### R39-04 — Medium — automated audit has product-claim blind spots

**Observed:** `scripts/audit.py` checks that a source hostname is allowlisted and that price/metal/ID match stored excerpts. It does not validate `name`, `category`, `karat`, or `priceScope` against field-level evidence; an allowlisted eCFR URL could satisfy the generic external-link check for a product row. It also hard-codes one accepted review date.

**Risk:** future unsupported edits to those fields could pass the “hallucination-risk” check. The supplied audit correctly disclaims that it is not a factual truth detector, so this is a coverage issue rather than evidence of a current false value.

**Requested disposition:** require field-level evidence for every populated fact, require retailer product URLs for product rows, validate the URL path/product identity, remove date hard-coding in favor of valid per-observation timestamps/staleness policy, and add negative tests proving unsupported edits fail. Preserve manual official-source review.

### R39-05 — Low — workflow actions are tag-pinned rather than commit-pinned

**Observed:** workflow uses `actions/checkout@v4`, `actions/setup-python@v5`, `actions/setup-node@v4`, `actions/upload-pages-artifact@v3`, and `actions/deploy-pages@v4`.

**Risk:** major-version tags are mutable supply-chain references. No malicious action behavior was observed.

**Requested disposition:** pin actions to reviewed full commit SHAs during final integration and retain automated update/review tooling if available.
